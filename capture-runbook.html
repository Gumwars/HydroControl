Eluktronics HYDROC-16 G1 · Linux port

Windows capture runbook

One session on a scratch Windows drive to observe what five rounds of Linux-side probing could not infer: the ITE 8233 chin bar wire format, and the values Control Center writes behind its performance modes.

What you're bringing back

The Windows drive is a capture rig, not a workshop. Everything gets implemented and tested back on Linux, so the trip succeeds if these files come home. Copy them to a USB stick, not the Windows partition.

  • chinbar.pcapngITE 8233 traffic while changing chin bar colour, brightness, and effect.
  • keyboard.pcapngITE 8291 traffic for per-key colour and effects — closes the kbctrl parity gaps.
  • actions.txtYour handwritten log of what you did and when. Without it the pcaps are far harder to read.
  • ec-*.txtEC memory-window reads, one per performance mode. Captured in Windows with no reboots — see phase 05.
  • battery-map.txtWhich Control Center battery label sits on which EC value — see phase 06.
01

Make room, then build the drive

Both M.2 slots are already populated: nvme0n1 holds your ESP and the LUKS root, nvme1n1 is the ext4 games partition. The spare has to displace one, and the games drive is the obvious candidate — that content is re-downloadable.

  1. Back up anything from /mnt/games you actually care about.
  2. Remove nvme1n1, fit the spare SSD in that slot.
  3. Also remove nvme0n1, then install Windows 11. With no other disk present, Windows is forced to create its own ESP on the spare.
  4. Refit nvme0n1. From here on, choose the OS from the firmware boot menu.
Why remove the Linux drive Windows will happily adopt an ESP it finds rather than making one. Yours sits on nvme0n1p1 beside a LUKS volume. Physically removing the disk during install is the only guarantee, and it takes one panel-off session — far cheaper than repairing a clobbered boot chain against an encrypted root.

Then install the Eluktronics Control Center from your existing Eluktronics Control Center.zip, and confirm the chin bar actually responds to it before capturing anything.

02

Install the tooling

  • Wireshark — during setup, tick the USBPcap component. That checkbox is the whole point; it's easy to miss.
  • RWEverything — for the EC reads in phase 05. You'll use its memory viewer, not its EC tab.
  • Reboot after installing USBPcap. It's a kernel driver and won't enumerate until you do.

Find the chin bar's capture interface — you want the root hub that 048d:7001 sits under:

Device Manager → View → Devices by connection
  → locate "ITE Device(8233)" → note its parent USB root hub

In Wireshark, that root hub appears as USBPcap1, USBPcap2, and so on. Capture on the one holding the 8233.

03

Capture the chin bar

This is the blocker, so it goes first while you're freshest. Discipline matters more than volume: one action per five-second window, with the wall-clock time written down. A dense pcap with no log is close to useless; a sparse one with a good log decodes quickly.

Start the capture, then walk this sequence, pausing five seconds between each and noting the time:

#Action in Control CenterWhat it isolates
1Chin bar → static / solid colour modeThe mode switch that stops the cycle
2Set solid red (255,0,0)Colour payload, known value
3Set solid green (0,255,0)Byte position of G
4Set solid blue (0,0,255)Byte position of B
5Set block 0 red, all others blackPer-block addressing
6Set block 6 red, all others blackBlock ordering and stride
7Brightness to minimum, then maximumBrightness field
8Switch back to the cycle effectEffect selector
9Change effect speedSpeed field
10Toggle the chin bar off, then onPower / enable command
Why these values Pure red, green, and blue at full scale produce FF bytes in exactly one position each. Three captures triangulate the channel order without any guesswork — and steps 5 and 6 pin down how the seven blocks are laid out, which is the part we could never infer from Linux.

Then: the EC cross-check

This settles a question five separate Linux experiments could not. With the chin bar left on solid red in Control Center, reboot straight into Linux — the EC holds its state across a warm reboot — and dump the lightbar registers:

sudo python3 ec_poke.py show
How to read it If 0749 RED comes back FF with APP_EXISTS set, then Windows drives colour through the EC and the ITE 8233 only gates power — the LIGHTBAR feature belongs back in the device descriptor. If those registers are still 00 while the bar was red, the EC path is genuinely unused on this model and the whole protocol lives in the USB capture.
04

Capture the keyboard

Same method against the ITE 8291 root hub. This is the bonus round — it closes the two known kbctrl gaps, and you're already set up.

  • Set one single key (say A) to red, everything else off — reveals the per-key frame format.
  • Set a second key far away (say Enter) — confirms the key-index ordering.
  • Pick an effect with a custom colour Control Center offers but kbctrl's palette lacks. This is the direct answer to "colour selections missing".
  • Set a per-key layout, then reboot into Windows without reopening Control Center. If the layout survives, the controller stored it — capture the write that did it, because that's your persistence fix.
05

Read the EC per performance mode

No reboots needed The EC is memory-mapped at 0xFE410000 — that is all \_SB.INOU.ECRR does under the hood. RWEverything's physical memory viewer reads that window directly from inside Windows, so you never leave the OS that is setting the modes.
Use the memory viewer, not the EC tab RWEverything's dedicated EC tab only reaches the legacy 256-byte port space and will not show these registers. That limitation is what made an earlier draft of this runbook call for a reboot per mode; it was wrong about the tool, not about the addresses.

In RWEverything: Access → Memory, jump to 0xFE410700, read through 0xFE4107FF. That is byte-for-byte the same window ec_dump.py prints on Linux, so the two are directly comparable.

Set each of these in Control Center, then capture the memory window (screenshot or Save):

FileControl Center state
ec-quietQuiet / Office mode
ec-balancedBalanced
ec-performancePerformance / Turbo
ec-pl-NNManual CPU power limit at a known wattage — write the wattage down

Registers to watch

  • 0x0783 / 0x0784 — PL1 / PL2, both 00 on this machine today.
  • 0x07A5 — FAN_QUIET (bit 2), OVERBOOST (bit 4), HIGH_POWER (bit 7). Currently 00.
  • 0x078E — FAN_CTRL, currently FC. Bit 6 (UNIVERSAL_FAN_CTRL) is already set, which is the gate for manual fan control.
Why the wattage matters PL1 and PL2 both read 00 today, which almost certainly means "firmware default" rather than zero watts. A single reading at a known wattage tells us the units — whether the byte holds watts directly, half-watts, or an index into a table. That one observation is worth more than the other three dumps combined.

Fallback. If the memory viewer is blocked, the EC keeps its state across a warm reboot: set the mode, reboot into Linux, and run sudo python3 ec_dump.py -o ec-quiet.txt. Slower, but equivalent.

06

Map the battery modes to their labels

The three charging modes already work on Linux — charge_types reports Trickle, Standard, and Long_Life, and the threshold is writable. What nobody has established is which Control Center label corresponds to which EC value. Getting that backwards means a UI that caps the battery when the user asked to fill it.

Same memory viewer, no reboots. For each of the three modes, set it in Control Center and read two bytes:

AddressMeaning
0x07A6Bits 5:4 = charging profile. 00 = HIGH_CAPACITY, 01 = BALANCED, 10 = STATIONARY
0x07B9Bits 6:0 = charge threshold percent. Currently 0x64 = 100

Record it plainly — Control Center's label, then both bytes:

Stationary   0x07A6 = __   (bits 5:4 = __)   0x07B9 = __ (__%)
Balanced     0x07A6 = __   (bits 5:4 = __)   0x07B9 = __ (__%)
Long Haul    0x07A6 = __   (bits 5:4 = __)   0x07B9 = __ (__%)
What this also answers If the threshold at 0x07B9 moves on its own as you switch modes, the EC drives the cap from the profile and the Linux UI should present modes as primary with the threshold read-only. If it stays at 0x64 for all three, the modes govern charge current rather than the cap, and they only differ while actually charging on AC.
Known anchor point Right now on Linux 0x07A6 reads 00 (profile HIGH_CAPACITY) while charge_types shows [Standard]. So EC 00 ↔ Linux Standard is already established — the only missing link is which Control Center name sits on it.
07

Come home

  • Copy the pcaps, actions.txt, and the EC dumps to a USB stick.
  • Also grab HKLM\SOFTWARE\OEM\GamingCenter2\RGBKeyboard after you've changed settings — the live values will show which of those seven MEZone_Lighbar* template variants your machine actually uses.
  • Leave the Windows drive intact. Firmware and EC updates ship as Windows executables, so it stays useful.

Back on Linux, the pcaps decode straight to packet bytes and we implement against them — no more guessing at framings.
