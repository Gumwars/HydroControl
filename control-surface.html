Control surface reference

Every path, packet, and register the UI binds against — with value ranges, what is writable, and what is still unmapped. Verified on kernel 7.1.8 with the patched uniwill-laptop module loaded.

Resolve, never hardcode

Two of these paths carry an index assigned at probe/enumeration order. They are stable across a given boot and not across reboots or USB changes. Hardcoding either is the single most likely source of "works sometimes" bugs — it already cost this project weeks on the chin bar.

Settings do not survive a power cycle The charging profile lives in volatile EC state. After a reboot, 0x07A6 reverts to 00 (HIGH_CAPACITY) regardless of what was selected — the driver never writes this register at probe, so nothing in Linux restores it. This is almost certainly why Control Center ships a background service: something has to re-apply EC settings at every boot. The frontend needs an equivalent (a systemd unit, or folding it into kbctrld), and the UI should read actual state at startup rather than trusting a stored preference.
Open question — do not label these in the UI yet Which Control Center name (Stationary / Balanced / Long Haul) maps to which token is unverified. The kernel's names come from another vendor's reverse engineering. Measurement so far: Trickle (EC profile 2) charged past 83% at full current with a perfectly honest gauge, so it does not cap the initial charge. Until the mapping is confirmed, show the raw tokens rather than guessing a friendly label — a mode that silently caps charging is worse mislabelled than unlabelled.

UI hint ac_auto_boot and usb_powershare_high cannot both be on — the driver rejects it. Present them as a three-way choice (neither / one / the other) rather than two independent switches that can enter an invalid state.

Chin bar — ITE 8233 working

8-byte feature reports over hidraw, HIDIOCSFEATURE(9) = 0xC0094806, report-id 0x00 prefixed. Protocol matches tuxedo-drivers ite_8291_lb.c and OpenRGB MR 3166. Setting colour or brightness turns the bar on; no commit needed.

ActionPackets
Static colour14 00 01 R G B 00 00
08 22 01 01 bri 01 00 00
Breathing08 22 02 speed bri 00 00 00
Off12 00 03 … → 08 05 … → 08 01 … → 1A … 01

bri is 0–100, speed 1–10. Colour goes into palette slot 1; the mode command is what makes it visible.

Not yet mapped Control Center models the bar as 7 colour blocks with per-block RGB (ColorBlocks: 7 in RGBKeyboard.reg), plus effects with speed and direction. Only whole-bar static and breathing are proven here. Mode bytes beyond 08 22 01/02 are unswept — that is where the remaining effects and any per-block addressing live.
Dead end — do not use The EC lightbar registers (0x0748–0x074B) and the uniwill:multicolor:status LED class accept writes but drive nothing on this model. LIGHTBAR was removed from the device descriptor for this reason, so that LED node no longer appears. Drive the bar over hidraw only.

Keyboard RGB — ITE 8291 working

USB 048d:600b, driven through kbctrl over ite8291r3-ctl (libusb, not hidraw). Bind to kbctrl rather than the device directly.

CapabilityRangeNotes
Effectsbreathing, wave, random, rainbow, ripple, marquee, raindrop, aurora, fireworksPer-effect params in EFFECT_PARAMS.
Effect colour8 palette names + randomBuilt-in effects take a palette index, not RGB.
Per-key colour(row, col) → RGBFull RGB. save flag writes to onboard storage.
Brightness0–100—
Persistence — resolved The save flag is now wired through apply_per_key and set_effect, so per-key colours and effects are written to the controller's onboard storage. They survive power loss and are restored by the keyboard itself before userspace starts, rather than being re-pushed by the daemon at boot. restore_palette() resets to the ITE factory palette.
Effect colours remain palette-indexed set_effect takes color_idx, not RGB — the firmware effects accept an index into the controller's palette, so effect colours are limited to the eight named entries plus random. Per-key mode is unrestricted RGB. Arbitrary colour in an animated effect would mean driving per-key frames from the host on a timer, which is a different mechanism rather than a missing parameter.

CPU power limits working

Verified end to end on this machine: setting 75 W produced 75.0 W sustained package draw, setting 45 W produced 45.0 W. Measured via the RAPL energy counter under stress-ng --cpu-method matrixprod.

StepRegisterValue
1. Arm custom profile mode0x0727 bit 6Set. The profile LED beside the power button turns white — the same indication Windows uses for a custom profile.
2. Write the limit0x0783 PL1_SETTING
0x0784 PL2_SETTING		Watts, directly. 0 = firmware default.
3. Confirm0x046A PL1L
0x046B PL2L		Live readback; mirrors the setting once applied.
Write to the setting, not the readback ECRW accepts writes to 0x046A/0x046B and reports success, but they do not persist — that window is the EC's live view. The write side is 0x0783/0x0784. Without step 1, writes are accepted and ignored.
Volatile — needs restoring at boot Both the 0x0727 latch and the PL values clear on power cycle, exactly like the charging profile. The same boot-restore service has to re-apply them.
Not the RAPL MSRs /sys/class/powercap/intel-rapl continues to report 205 W throughout — the EC enforces its envelope outside the MSR path. Any UI showing "current power limit" must read the EC, not RAPL. Actual draw is only observable through the RAPL energy counter under load.

Also present: 0x046F PL4L = 125 W (peak), 0x046E PL3L = 0, and 0x0466 bit 0 = turbo enable.

Escape hatch: direct EC access

The DSDT exposes the EC as memory-mapped I/O at 0xFE410000, wrapped by \_SB.INOU.ECRR (read) and \_SB.INOU.ECRW (write), serialised behind the ACPI mutex UWOL. With acpi_call loaded, userspace can reach any register — including those the driver deliberately withholds.

sudo modprobe acpi_call
sudo python3 ec_dump.py                 # annotated dump of 0x0700-0x07FF
sudo python3 ec_poke.py read 0x7A6      # single register
Reads yes, writes no ECRW validates nothing. This is a debugging tool, not a UI backend — the frontend should never call it. The driver's regmap whitelist exists precisely to stop writes to registers whose semantics are unknown, and a bad PL1 value is among the few things here that can require a battery-disconnect to recover.

Privileges

Every write above needs root today, and hidraw needs root even to open. A GUI should not run as root. Two udev rules move almost everything to a group:

# /etc/udev/rules.d/99-hydroc.rules
KERNEL=="hidraw*", ATTRS{idVendor}=="048d", ATTRS{idProduct}=="7001", \
  GROUP="plugdev", MODE="0660"
KERNEL=="hidraw*", ATTRS{idVendor}=="048d", ATTRS{idProduct}=="600b", \
  GROUP="plugdev", MODE="0660"

SUBSYSTEM=="platform", KERNEL=="INOU0000:00", \
  RUN+="/bin/sh -c 'chgrp plugdev /sys%p/fn_lock /sys%p/super_key_enable \
  /sys%p/touchpad_toggle_enable /sys%p/ac_auto_boot /sys%p/usb_powershare_high \
  /sys%p/ctgp_offset; chmod g+w /sys%p/fn_lock /sys%p/super_key_enable \
  /sys%p/touchpad_toggle_enable /sys%p/ac_auto_boot /sys%p/usb_powershare_high \
  /sys%p/ctgp_offset'"

Battery attributes under power_supply are the awkward case — they are recreated on hotplug events, so a udev rule there is fragile. A small privileged helper (the existing kbctrld pattern, or a polkit action) is the sturdier route for charge_types and the charge threshold.

Verified on kernel 7.1.8-1-cachyos-bore with the patched uniwill-laptop module. The device descriptor is a local addition and not upstream, so a stock kernel will expose none of the platform or battery attributes.
